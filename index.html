Looped Weight-Space Programming: LLM-Written Transformers for Long Algorithmic Reasoning

AuthorsAbdelrahman Elsayed*, Ahmed Heakl*, Abdelrahman Shaker, Fahad Khan, Salman Khan, Claude Opus 5.5* Equal contribution
Affiliation

We asked Claude to solve hard 30×30 mazes from Maze-Hard, and it failed on 74% of them. We then asked it to write a transformer instead. It set all 19,936 weights by hand for $19, with no training, and that transformer solves 100%, even on 100×100 mazes. With a 1,000-weight cap, Claude wrote one with only 928, 1,900× fewer than models like LDT and EBR, that still solves 100%. The trick is the loop. One small block repeats one step as long as needed, so a transformer Claude wrote loops over 2 million times on a 20-disk Tower of Hanoi without making a single mistake.

Deep learning models normally get their weights from training. Once a transformer is trained, though, it is nothing more than a program written in matrices. If you know the program you want, you can skip training and write the matrices yourself. People have done this by hand for small problems (related work). Compilers such as Tracr go further, turning short programs into transformer weights automatically. Recently, Weight-Space Programming (Takehi, Teoh, Zhang and Khattab, MIT CSAIL) showed that a frontier LLM can edit a model's weights directly, without any training. Other groups have gone further and had LLMs set every weight of a tiny transformer, but only for toy tasks (Singh, AdderBoard). In those transformers, every step of a computation takes a separate block. Scaling one up to a hard problem would mean a far bigger transformer and a far bigger Claude bill, since Claude would have to write every one of those extra weights.

We wanted to know whether LLM-written weights hold up on problems that need long chains of reasoning. Our main test is Maze-Hard, a benchmark of 30×30 mazes whose shortest paths run longer than 110 steps. Frontier LLMs struggle with it. For example, when Claude Opus 5.5 is asked for the shortest path, it solves only 26% of the test mazes it is given [1]. So instead of asking Claude to solve the mazes, we asked it to write a looped transformer that solves them, setting every weight by hand.

The transformer has a single block with 19,936 weights. This block runs in a loop. Each forward pass moves a shortest-path search one step further, so the transformer keeps feeding the maze back through the same block until the path is complete. With enough passes, it solves 100% of the test mazes. That is more than the newest looped models trained for this benchmark reach. Energy-Based Reasoners (EBR) [2], one of the strongest of them, trains 1.8 million weights on 1,160 PFLOPs of compute and solves 94.1%.

That loop is what this post adds to earlier work on writing weights. With it, one block can run thousands to millions of steps, so the number of weights does not grow with problem size. We call this approach looped weight-space programming.

Claude itself struggles to carry out a search of more than a hundred steps in text, even when we spell the algorithm out (section 3). Yet it can write a single step of that search into weights, leaving the loop to repeat the step for as long as the maze requires. Programmers rely on the same trick whenever they write code for arithmetic they could not do in their heads. Language models gain from it too. On math word problems, they get more answers right when they write a short program that does the arithmetic than when they do the arithmetic in text [3, 4].

Writing the weights by hand also makes the transformer easy to read. A trained model spreads its algorithm across millions of numbers, so recovering that algorithm takes substantial analysis. A whole study was needed, for example, to show that a small transformer trained on modular addition computes it with sines, cosines and trigonometric identities [5]. The constructed transformer has explicitly assigned state variables and operations. Claude decided what every number inside it stands for before it set a single weight, so we can read those numbers after any loop and watch the search spread across the maze (section 6).

The goal is not just to replace conventional algorithms with transformers. It is to understand whether algorithmic reasoning can be explicitly programmed into neural networks rather than acquired through gradient-based training. This gives us interpretable solutions to difficult reasoning tasks, helps separate optimization failures from architectural limitations, and opens the possibility of combining learned representations with reliable algorithmic computation.

We hope these hand-written transformers help advance research on looped models, by showing how much a single small block can compute when it runs in a loop and by giving training methods concrete solutions to aim for. Since every number inside them is known, they can also serve as test cases for interpretability tools. The weights and two in-browser demos are public.

1. How the maze transformer works

In a Claude Code session, Claude designed every weight itself, filling in the weight matrices with code, and we ran it on the test mazes only once, at the end (appendix A gives its task description). Claude made each cell of the maze one token, so a 30×30 maze becomes 900 tokens. It gave each cell a memory of 35 numbers, which the transformer carries from one loop to the next. Claude decided what each of these numbers stands for. A few of them record what the cell is (a wall, the start cell or the goal) and where it sits in the grid. Other numbers track the search. They hold the cell's distance from the goal, which neighbor is its next step and whether it lies on the path. The remaining 20 numbers serve as scratch space for whatever the cell reads from its neighbors. The transformer's single block has four attention heads, each with a single job. One lets every cell read the cell below it, while the other three read the cell to its left, to its right and above it. Claude then set every weight so that each loop updates these numbers the way it intended.

The math

Cell \(c\), at row \(r_c\) and column \(c_c\), starts as the sum of three table rows. They put \(1\), \(r_c\), \(c_c\) and \(r_c^2 + c_c^2\) into its first four numbers and its type into the next three.

The head that looks in direction \(\delta = (\delta_r, \delta_c)\), one of \((1,0)\), \((0,-1)\), \((0,1)\) and \((-1,0)\), scores every cell \(n\) by

\[ \frac{q_c \cdot k_n}{\sqrt{8}} \;=\; -100\,\big[(r_n - r_c - \delta_r)^2 + (c_n - c_c - \delta_c)^2\big] \;+\; \mathrm{const}(c). \]

The neighbor at \(c + \delta\) scores 100 more than any other cell, so the softmax puts a weight of \(1 - O(e^{-100})\) on it. The head copies five of that neighbor's numbers into five scratch numbers of \(c\). These are its three count numbers \(m_0, m_1, m_2\), its path flag and a binary number that is 1 when it points back at \(c\).

With this layout, each pass through the block performs one step of a standard shortest-path search.

A wave from the goal. The goal starts at distance 0. On every loop, each open cell that has not been visited yet but borders a visited cell takes that neighbor's distance plus one. The visited area therefore spreads outward from the goal one step per loop.

The math

Write \(m_k(c) \in \{0, 1\}\) for the binary number that is 1 when the count of cell \(c\) is \(k\), and \(\mathcal{N}(c)\) for its four neighbors. Two wave neurons for each \(k\) compute

\[ m_{k+1}(c) \;\mathrel{+}=\; \tau\Big(2\!\!\sum_{n \in \mathcal{N}(c)}\!\! m_k(n) \;-\; 8\,\big[\mathrm{wall}(c) + m_0(c) + m_1(c) + m_2(c)\big] \;-\; \tfrac12\Big), \qquad \tau(z) = \mathrm{ReLU}(z) - \mathrm{ReLU}(z - 1), \]

with the index \(k+1\) taken mod 3. The argument of \(\tau\) is at least \(1.5\) when the cell is not a wall, has no count yet and has a neighbor with count \(k\). Otherwise it is at most \(-0.5\), so \(\tau\) gives 1 or 0. After loop \(t\), the cells with a count are the ones at most \(t\) steps from the goal.

Distance modulo 3. Apart from the position, every number in a cell's memory is binary, either 0 or 1. A cell therefore cannot store its distance to the goal as an ordinary number. Instead, it stores the remainder of that distance divided by 3, using three binary numbers, one for each remainder 0, 1 and 2. For example, a distance of 7 leaves a remainder of 1, so it is stored as 0, 1, 0. This is sufficient for the search. Two visited cells next to each other differ in distance from the goal by one, so the remainder is enough to tell which neighbor is one step closer to the goal. As a result, the transformer's size does not depend on maze size.

The math

Let \(d(c)\) be the length of the shortest path from cell \(c\) to the goal. Every step in the grid changes \(r + c\) by one, so \(d\) has opposite parity on neighboring cells. Two open neighbors \(c\) and \(n\) therefore satisfy \(|d(n) - d(c)| = 1\), and

\[ d(n) = d(c) - 1 \quad\Longleftrightarrow\quad d(n) \equiv d(c) - 1 \pmod 3, \]

since the two cases \(d(c) \pm 1\) differ by 2, which is not a multiple of 3. Counting mod 2 would fail, because \(d(c) + 1 \equiv d(c) - 1 \pmod 2\). Three binary numbers per cell are enough however large the maze is.

Pointers. Each cell also has four binary numbers, one for each direction, down, left, right and up. Once a cell is visited, it sets the number for the direction of a neighbor one step closer to the goal to 1 and keeps the other three at 0. We say the cell points to that neighbor. A neighbor is one step closer when its remainder is one less than the cell's, with 2 counting as one less than 0. When several neighbors qualify, it picks the first in the fixed order down, left, right, up.

The math

Each cell has four binary pointer numbers \(p_\delta(c)\), one per direction, taken in the order \(\delta_1, \dots, \delta_4\) = down, left, right, up. They are rewritten in every loop. Eight reset neurons, two per direction, cancel the old value, since \(p - \mathrm{ReLU}(p) + \mathrm{ReLU}(-p) = 0\). At the same time, 24 pointer neurons compute

\[ p_{\delta_j}(c) \;=\; \sum_{k=0}^{2} \tau\Big(2\,m_k(c) + 2\,m_{k-1}(n_{\delta_j}) - 2\sum_{i<j} m_{k-1}(n_{\delta_i}) - 2.5\Big), \]

where \(n_\delta\) is the neighbor in direction \(\delta\). The argument reaches \(1.5\) only when \(n_{\delta_j}\) is one step closer to the goal and no earlier direction is. That is the tie-break.

The path. As soon as the wave visits the start cell, a path grows out of it one cell per loop, following the pointers all the way to the goal. These cells form the answer. On the first test maze, the wave visits the start cell at loop 111. The path then takes another 111 loops to grow, so it is complete at loop 222. A maze therefore needs twice as many loops as its shortest path is long. A shortest path passes through each cell at most once, so twice the number of cells covers any maze. The transformer runs that many loops, 1,800 on a 30×30 maze, 7,200 on a 60×60 maze and 20,000 on a 100×100 maze. Claude checked the transformer on the 1,000 training mazes, all 30×30, and on mazes it generated itself, up to 45×45. We then ran the transformer on 50 mazes of 60×60 and 40 of 100×100, with up to eleven times as many cells, and it solved every one, with the same weights and no retraining. A bigger maze only takes more passes. The block does one step of the search, and one step is all a maze of any size needs.

The math

The start's path flag is 1 from the embedding. A cell joins the path when a neighbor on the path points at it,

\[ \mathrm{on}(c) \;\mathrel{+}=\; \sum_{\delta} \tau\big(2\,\mathrm{on}(n_\delta) + 2\,p_{-\delta}(n_\delta) - 2\,\mathrm{on}(c) - 2.5\big), \]

where \(p_{-\delta}(n_\delta)\) is the neighbor's pointer back toward \(c\). The readout scores the five characters at every cell,

\[ \ell_{\#} = \mathrm{wall}, \quad \ell_{\text{space}} = 1 - \mathrm{wall} - \mathrm{start} - \mathrm{goal}, \quad \ell_{S} = 3\,\mathrm{start}, \quad \ell_{G} = 3\,\mathrm{goal}, \quad \ell_{o} = 2\,\mathrm{on}, \]

and writes the highest. A path cell becomes o, while the start cell and the goal keep their letters, because \(3 > 2\).

Every binary number is written through \(\tau(z) = \mathrm{ReLU}(z) - \mathrm{ReLU}(z - 1)\), which is flat at 0 for \(z \le 0\) and flat at 1 for \(z \ge 1\). The arguments above land at \(1.5\) or below \(-0.5\), so an error below \(0.5\) in an argument leaves the output unchanged. The softmax leak of about \(e^{-100}\) per cell sits far inside that margin. Forty clean-up neurons, two per scratch number, then erase what the heads copied,

\[ s \;\leftarrow\; s - \mathrm{ReLU}(s) + \mathrm{ReLU}(-s) \;=\; 0. \]

Let \(D = d(S)\) be the length of the shortest path. The wave gives the start cell a count at loop \(D\). The path then grows one cell per loop along the pointers and reaches the goal at loop \(2D\). A shortest path visits each cell at most once, so \(D < n\) for a maze of \(n\) cells, and the loop count \(R = 2n\) covers every maze of that size.

Extra loops don't undo the answer

Looped models trained by gradient descent can overthink, which means their answers get worse when they run for more loops than they were trained with. Bansal et al. (NeurIPS 2022) showed this on mazes with DeepThinking, a looped convolutional model trained on 9×9 mazes. On 13×13 mazes it peaks at 86% after about 40 loops. If it keeps looping, its accuracy collapses below 1% by loop 82. The maze transformer avoids this by construction. Once the path is complete, every cell already holds its final distance, pointer and path flag, so another loop leaves every number as it is.

We see the same contrast on reasoning chains, puzzles that follow a chain of statements such as x0 = 7 and x1 = x0 + 3 for 1 to 8 steps to find one variable. A looped transformer trained on them by gradient descent solves 69.1% with its usual number of loops, but only 49.2% when it runs four times as many. The chains transformer Claude wrote stays at 100% up to 128 times its usual loops, which is about 1,500 loops on average. Not every trained looped model overthinks, though. Figure 6 shows that HRM and TRM hold their Maze-Hard accuracy at four times the steps they were trained with, although they level off near 82% and 92%.

2. How it compares on Maze-Hard

Maze-Hard comes from the HRM paper (Hierarchical Reasoning Model). It has become a standard test for small models trained to reason by repeating a step many times, such as HRM, TRM (Tiny Recursive Model) and the Lattice Deduction Transformer (LDT). Most of its mazes have several equally short paths, of which the dataset marks one as the answer. Figure 8 uses the LDT paper's scoring, where any shortest path counts.

The written transformer tops the chart. Frontier LLMs trail far behind, with none of the three that Davis et al. tested solving more than 26%. In an earlier version of the same paper, in April 2026, Claude Opus 4.6, DeepSeek V4-Pro and GPT-5.4 solved 0% of the test mazes. The trained looped models do much better, with LDT coming within 0.2 points at 99.8%. Yet LDT needs 90 times as many weights, whereas the written transformer needed no gradient training.

The 19,936 weights are not a minimum. We gave five fresh Claude Code sessions only the task and a cap on the number of weights, of 1K, 5K, 10K, 20K or 40K. All five kept the accuracy at 100%. The smallest needs only 928 weights, 1,900 times fewer than LDT.

3. Why Claude can write the transformer but can't solve the maze

Throughout, Claude is Claude Opus 5.5. When it solves a task itself, it answers in text, and when it writes a transformer, it works in a Claude Code session. As a check, we also had Claude solve 50 mazes in text inside Claude Code, with no tools. It found the shortest path in 38% of them, against 48% through the API with the “told how to search” prompt described below. Perhaps Claude scores low simply because it doesn't approach the maze systematically. To test this, we started from the LDT paper's prompt, in which Claude sees the maze as 30 lines of 30 characters and answers by writing out the same grid with the cells of its path marked. We then changed one thing at a time.

  • Told how to search. A paragraph added to the paper's prompt tells Claude to spread out from the goal one step at a time, then walk back from the start cell.
  • + one cell per token. Claude reads text in tokens, chunks of a few characters, so in a plain grid one token can cover several cells, such as a run of walls. Here, the cells are separated by spaces, with a dot for each free cell, so that Claude reads each cell as a separate token.
  • + answer with the path only. Instead of writing out the whole grid, Claude answers with the list of cells on its path, as (row, column) coordinates from the start cell to the goal.
  • + path only, no grid. Claude answers with the path as above. The maze also comes as a list of the (row, column) coordinates of its free cells instead of a grid.

Describing the algorithm lifts Claude from 26% to 48%, but accuracy stays at or below 50%. Tokenization does not explain the gap either, since giving Claude one token per cell made it no better (44% against 48%). These results suggest that execution errors contribute to the low accuracy. Every step along the path has to be right, yet Claude's first wrong step comes a median 35% of the way along it, even when it is told how to search.

Writing the transformer is a different task. Claude does not run the search. It designs one step of it, sets the weights to match and leaves the loop to do the running. We suspect this helps because each design choice can be checked separately, whereas solving the maze directly needs a long chain of steps that must all be right.

Writing the transformer was also cheap. The session that wrote the maze transformer produced 196,771 output tokens and cost about $19 at Claude Opus 5.5's API list prices. That is about as many tokens as Claude spends answering only 14 of the 1,000 test mazes in text. Answering all of them would take 73 times more. Claude had the final weights 39 minutes after it received the task. Claude worked from a task description, which appendix A gives in full. Solving mazes directly, by contrast, cost $0.14 to $0.34 for every maze in our runs, yet found the shortest path in at most half of them. The written transformer pays for itself after about 55 to 134 mazes and needs no API calls after that. Claude wrote all the transformers in this post in 18 sessions. Each session cost between $1.19 and $37.06, with a median of about $4.

4. Can training find these transformers?

If a transformer of 20,000 weights can solve every maze, why don't trained models of that size? Perhaps the architecture is the secret, in which case training would find the solution too if it had the same one. So we gave gradient descent the same starting point Claude had. We took the transformer Claude wrote, reset its weights to random, and trained it on the same 1,000 training mazes.

We trained these models:

  • The transformer Claude wrote, reset to random weights. As written, without normalization, in 6 runs (3 learning rates × 2 seeds). Then with RMSNorm added, in six versions of 8 hours each: the original size at three learning rates, twice the loops, 2 or 4 blocks per loop, and 4 or 16 times the width, up to 2.8 million weights.
  • The same six versions with a curriculum, from 10×10 mazes up to 30×30, with 2,000 more mazes we generated.
  • A class-balanced loss, alone and together with supervision of the distance and pointer states after each loop, at three learning rates.
  • A plain transformer encoder the size of TRM (8 blocks, width 256, 8 heads, 6.4 million weights, no loop), with a standard recipe on 3,000 mazes.
  • TRM itself (6.8 million weights), with its authors' recipe on one GPU.

Every run of Claude's architecture solved 0% of the test mazes. Without normalization, the first six runs broke down within 30 steps. With RMSNorm added, training ran smoothly, yet every transformer learned only to copy the maze back, which already gets 87.4% of cells right because only about one cell in eight is on the path. Versions up to 2.8 million weights, and a curriculum that started from 10×10 mazes, also stayed at 0% after 8 hours each. To do better, a transformer has to mark path cells, which in the written transformer happens only after a chain of a hundred or more steps that each have to be right. Our guess is that gradient descent finds no partial credit along the way.

Two fixes aimed at the copying did not help either. One weighted the loss so that path cells count as much as all other cells. The other also supervised the distance wave and the pointers after every loop. Both stopped the copying, yet none of the 185 checkpoints trained this way solved a single test maze.

A standard transformer [9] does better, though not nearly well enough. We trained a plain transformer encoder the size of TRM (8 blocks, 6.4 million weights, 320× the transformer Claude wrote) on 3,000 mazes for 8 hours on one GPU. It got 94–99% of its training mazes right yet solved only 46% of the test mazes at best, leveling off for its final two hours. TRM [8], a looped model built for this benchmark, reaches 91.6%.

Each of our gradient descent runs used about 5 PFLOPs, 230 to 2,000 times less than the trained models. So these runs show that gradient descent did not find the weights under the settings tested, not that the weights cannot be learned. Claude, meanwhile, simply wrote them, for about $19. The architecture holds a solution that scores 100%, yet training on the same data got nowhere near it.

Running the written transformer is cheap as well. At the 1,800 loops we use by default, it spends 2.2×1011 operations per maze, about 14 times fewer than HRM (3.0×1012) and 17 times fewer than TRM (3.8×1012) at the 16 reasoning steps they were trained with. Just 306 loops solve every test maze, at 3.7×1010.

Generalization beyond the checked sizes

Mazes test whether training can find a solution at all. A second question is whether a solution keeps working as problems grow. We tested this on three simpler tasks where problem size is easy to control. While writing each transformer, Claude could check it only on small inputs, which we call its checking range. We trained standard models on those same sizes, then tested both the written and the trained models on much larger problems.

Graph search. The task is to find the shortest route from point A to point B on a map, or to report that B cannot be reached. A map is a graph whose points, or nodes, are joined by one-way links, and it is full of dead ends and decoys. Claude checked its transformer on maps of up to about 12 points with routes of up to 4 steps. We then tested it on maps of up to about 48 points with routes of 8 to 16 steps, where it reached 100%. Trained models up to 99 times bigger stayed at 0% on those routes, including one that reached 97.4% on the checking range. The written transformer tracks which points it can already reach from A. On every loop, each visited point passes that status along its outgoing links, so a longer route simply takes more loops.

Parity. The question is whether a string of 0s and 1s contains an odd or even number of 1s. Claude checked the written transformer only on strings of up to 20 bits, yet it is correct at every length we tried, up to 4,095 bits. The trained models mastered the checking range but fell to chance (45.5–53.8%) on 21 to 128 bits.

Reasoning chains. Each problem is a set of shuffled statements such as x2 = x1 + 5. x0 = 7. x1 = x0 + 3., followed by a question about one variable. Claude checked the written transformer on chains of up to 8 steps, yet it is correct at 12, 16, 24 and 32 steps, and up to 63 in a harder extra test. The best trained model reached 93.7% within its training lengths but only 3.5% beyond them.

In all three tasks, the trained models do well on training sizes but fail beyond them, whereas the written transformers only need more loops. The written transformers show that size-independent solutions exist in these architectures. Each written transformer still has a size limit, set by its tables, its loop budget and its arithmetic precision rather than by the loop itself. Below that limit, the written transformer's answers are exact at every size we tested (appendix B). The full tables for all three tasks are in appendix C.

5. Far beyond mazes, from Sudoku to a million-move Tower of Hanoi

Mazes are only the beginning. Claude wrote transformers for eight more tasks from well-known benchmarks, most of them tasks where LLMs or trained models struggle. Each one solved every test problem we gave it (Figure 14).

Sudoku-Extreme, solved by guessing and backtracking

The maze transformer has no need to take anything back, because once the wave visits a cell, that cell's distance is final. Hard Sudoku is different, since sometimes the only way forward is to guess. Sudoku-Extreme is the hard Sudoku benchmark from the HRM paper, also used by TRM and LDT. Each puzzle is a 9×9 grid with some digits filled in and a unique solution. Even the newest frontier LLMs solve only 54% to 68% of them. Claude Opus 5.5 solved 54% of the puzzles it was given when asked directly.

The Sudoku transformer Claude wrote applies constraint propagation and backtracking to all 81 cells in parallel. Each cell keeps a list of the digits it could still be. Three attention heads let it read its row, its column and its 3×3 box, so it can cross out digits already taken and spot a digit that has only one place left. When nothing more can be crossed out, the transformer has to guess. It first saves a copy of the whole grid in memory, then guesses a digit for the cell with the fewest options and carries on. Should the guess lead to a contradiction, such as a cell with no digits left, the transformer restores the saved grid, in which that guess is now ruled out. One step of this search takes five blocks, which the transformer runs for 40,000 loops with room for 24 saved grids.

The Sudoku transformer solved every one of the 141,040 test puzzles we ran, including the first 10,000 on which HRM, TRM and Sotaku v2 are evaluated. On those puzzles, the best trained model, Sotaku v2, reaches 98.96%. The cost is compute. Because the transformer runs all 40,000 loops on every puzzle, it does about 50 times more arithmetic per puzzle than TRM, even though half the puzzles are solved within 273 loops and 99% within 3,213. The full comparison, the arithmetic per puzzle and the search's limits are in appendix D. On one H200 it takes about 0.8 seconds per puzzle.

With fewer loops, Claude moved the work into the block. We gave a fresh Claude Code session the same task with at most 1,000 loops, 40 times fewer. It wrote the same kind of solver but stacked 12 copies of its search step into the looped block, so that 1,000 loops give 12,000 steps. That transformer has more weights, 267.9K, but needs a third of the arithmetic per puzzle, and it solved all of the first 10,000 test puzzles.

Tower of Hanoi up to 20 disks

Tower of Hanoi became a famous test of long reasoning after The Illusion of Thinking [10] showed reasoning models collapsing on it. When o3-mini, DeepSeek-R1 and Claude 3.7 Sonnet Thinking wrote out every move without tools, they began to fail at 7 to 8 disks, even when given the solution algorithm. The goal is to move a stack of disks from the first peg to the third, one disk at a time, with no larger disk placed on a smaller one. Each extra disk roughly doubles the number of moves. Twenty disks take 1,048,575 moves. A single wrong move makes the answer wrong.

The Hanoi transformer Claude wrote outputs one move at a time, the way a language model writes text, feeding each move back in as input. Before every move, its attention reads the starting position and every move written so far, which tells it where each disk is now. The rest of the block turns that position into the next move. Because the transformer works out the position from scratch at every move instead of keeping a running tally, errors cannot accumulate. The Hanoi transformer is a single looped block with only 3,686 weights. Checker Jumping, newer models and the transformer's limits are in appendix E.

Writing out the 1,048,575 moves for 20 disks takes the transformer about 9×1013 operations, about 89 million per move, since each move looks back over every earlier one.

GraphWalks, where the question sits in a million-token prompt

GraphWalks is OpenAI's benchmark for very long prompts. Each prompt lists one-way links between nodes, then asks which nodes lie at a distance of N steps from a given node. We used its longest set, 200 problems of 256k to 1M tokens, each up to about 1.75 million characters long.

The GraphWalks transformer works like the maze transformer, with links in place of cells. On every loop, one attention head lets each link check whether a link into its starting node has already been visited, so the visited area grows by one step per loop. At the end, every node at a distance of N steps from the start writes its name into the answer. The transformer scores 100% (F1) on all 200 problems. On the same set, Claude Opus 5.5 scores 66.8%, while Gemini 4 Carbon, the best LLM in Google's published results, reaches 96.2% (appendix F).

BIG-Bench reasoning questions, written in plain English

Claude also wrote transformers for four reasoning tasks from BIG-Bench, where each question is written in plain English. Like an LLM, each transformer reads the question as text and writes its answer as text. Two tasks come from BIG-Bench Hard [11]. Boolean Expressions asks for the value of an expression such as not ( True and False ) or False, and Dyck Languages asks for the brackets that close a sequence such as [ { ( ) <. The other two come from BIG-Bench Extra Hard [12], a much harder version made once frontier models had mastered BIG-Bench Hard. Web of Lies asks who is telling the truth, given a long chain of people's claims about each other. Shuffled Objects asks who holds which object after a long series of swaps.

Each transformer turns its question into something it can loop over. The Boolean transformer simplifies the expression one step per loop, much as you would by hand. The Dyck transformer adds up openers and closers to find how deep each bracket sits, then closes the most recent bracket that is still open, one at a time. In Web of Lies, each person's claim concerns someone else. On every loop, everyone whose subject is already settled works out whether they are telling the truth, so the answers spread along the chain of claims. Shuffled Objects uses a doubling trick from parallel computing. On every loop, each position merges its record of swaps with the record twice as far back, so after only a few loops the last position knows the outcome of all of them.

All four transformers score 100%, both on the 250 official test items of each BIG-Bench Hard task and on all 180 test questions of each Extra Hard task. The Extra Hard results are the more informative ones. There, the best LLM results we found are 81.2% on Web of Lies and 56.9% on Shuffled Objects, the latter achieved by having the model write and run a program. On BIG-Bench Hard, frontier LLMs already score above 90% (Kazemi et al., 2025), so we compare only with small open models and treat the result mainly as proof that the transformers can read text. The full tables and the format tests are in appendix G.

Graph algorithms, SAT and planning

We then took the recipe to three benchmarks of other kinds of algorithms. From CLRS-30, in its text version CLRS-Text, Claude wrote transformers for three algorithms beyond search: strongly connected components, minimum spanning trees with Prim's algorithm, and the longest common subsequence, a dynamic program. From SATLIB came small random 3-SAT formulas, satisfiable and unsatisfiable, which the transformer must decide, giving a satisfying assignment when there is one. From PlanBench came the Blocksworld, Mystery Blocksworld and Logistics planning tasks, where every plan is checked for validity. Each transformer was written by a fresh Claude Code session from a plain description of the task, checked on the training split and run once on the test split.

The test splits hold larger inputs than the training splits. The components transformer is exact on graphs of up to 22 nodes, where the largest training graph had 15, and the subsequence transformer on strings of up to 15, beyond the training maximum of 10. The SAT transformer runs a complete search, one step per loop, and answers only when the search ends. Every assignment it gave satisfies its formula, every "unsatisfiable" is right, and the hardest formula used 808 of its 1,224 loops.

Claude on its own did well on planning but slipped on SAT. It gave 10 assignments that do not satisfy their formula and missed 9 of the 50 unsatisfiable formulas, after a median of 88,309 output tokens on each of those.

6. Weight-space writing is interpretability by construction

Interpretability research usually works backwards. It starts from a trained model and tries to work out what its numbers mean, by probing hidden states, switching parts off and tracing the circuits that connect them [13]. A hand-written transformer works the other way around. Claude chose the meaning of every number first and then set the weights to match, so the explanation is fixed before any weight is set.

For the maze transformer, this makes the usual interpretability questions easy to answer. We can read any cell's distance, pointer and path flag after any loop, which is how Figure 2 and the maze demo show the search as it runs. We can also predict what breaks before we break it. Each attention head carries the wave in one direction, so removing a head should stop the wave from crossing that way. On the 1,000 training mazes, it does. Without any one head, the wave stalls after visiting only 8.2–8.6% of the cells it should, so 0% of the mazes get solved. Finally, we can check the inside of the transformer against the algorithm rather than only its output. After the last loop, every cell's distance, pointer and path flag match those of a standard shortest-path search on all 1,000 training mazes.

The meanings can also be read back from the weights alone. We gave three fresh Claude Code sessions only the maze transformer's weights and a bare description of its architecture, without the word maze, the task or any example, and asked what it computes and what each of a cell's 35 numbers stands for. Each recovered the whole design, 11 of 11 points on a rubric fixed in advance, in about two minutes, and confirmed it by running the weights against its shortest-path search on random grids. The same transparency makes these transformers test cases for interpretability tools (appendix H).

This readability depends on knowing the algorithm in advance. The transformers are easy to read because Claude knew the algorithm before it wrote them, which suits tasks with a known algorithm better than open-ended ones such as language.

Conclusion

  • The approach works beyond mazes. The same recipe gave transformers that solve Sudoku-Extreme, a 20-disk Tower of Hanoi (1,048,575 moves without a mistake), GraphWalks prompts of up to a million tokens and four BIG-Bench reasoning tasks, each on 100% of its test problems. Seven more cover graph algorithms and a dynamic program from CLRS-30, SAT and planning.
  • The loop keeps the transformers small. A bigger problem needs more passes, not more weights. This keeps the maze transformer 163 times smaller than it would be without a loop, and lets each transformer work far beyond the sizes Claude checked (section 4).
  • Gradient descent did not find these solutions. Trained from random weights on the same 1,000 mazes, the architecture of the maze transformer solved 0% in every run (section 4).
  • Every number has a meaning. Claude decided what each number stands for before setting any weight, so we can watch the algorithm run (Figure 2, section 6) and use these transformers as test cases for interpretability tools (appendix H).

More broadly, our results suggest that for algorithmic tasks with a known procedure, what holds small models back is not their size but finding the right weights. An LLM that cannot solve a problem directly may still write a transformer that does.

What's next

We plan to study multitask composition and training initialized from constructed weights. The first is a single transformer for many tasks, in which the modules from this post live side by side while a hand-written router sends each input to the right one. The second is to use hand-written weights as a starting point for training. Inference is the generic loop: embed → the same block R times → readout.

  reformatted.

  - The answer is the written strings in position order.
  - The harness passes that string to the grader unchanged, with nothing added. Your network must write everything

BThe limits of each transformer

A written transformer gives the right answer at a given size when three conditions hold. First, its tables must be large enough. The maze transformer reads grids of up to 128 × 128 cells, the parity transformer strings of up to 4,095 bits and the graph search transformer node numbers up to 63. Second, its loop rule must give enough loops. The maze transformer runs twice as many loops as the maze has cells, more than any path needs. Third, its arithmetic must be precise enough. Each attention head prefers its target by a wide margin, so almost no attention goes to other positions, and after every loop each value is snapped back to a clean 0 or 1, so small errors cannot add up.

Within these limits, correctness follows by induction over loops. If every value is right before a loop, the loop computes the algorithm's next step, so after enough loops the transformer holds the algorithm's final answer, and further loops leave it unchanged. Larger inputs only need larger tables, which the same formulas write, while the looped block stays the same.

The other transformers have limits of their own, given in their sections. The Sudoku transformer has room for 24 saved grids and runs 40,000 loops (appendix E). The Tower of Hanoi transformer needs 64-bit arithmetic and handles at most 20 disks (appendix F). The GraphWalks and BIG-Bench transformers read only the prompt format they were built for (appendices F and G).

ETower of Hanoi and Checker Jumping in full

Tower of Hanoi. The puzzle needs no search, since each move follows from a simple rule, so it tests long, error-free execution. Part of the debate around the Apple paper, The Illusion of Thinking, was whether the models' collapse on larger puzzles came from output limits. The authors replied that the first errors appear early, around move 40 at 8 disks. Newer models still fail early. In 2026 tests, o4-mini failed from 6 disks, while Qwen3-235B-Thinking fell to about 52% at 7 disks and 20% at 8 (Pushkin and Abbe, 2026, read from a plot).

LLMs do finish the puzzle with outside help. With code execution, reasoning models solved every size they were tested on, up to 13 disks [14]. MAKER [15] solved 20 disks by asking an LLM for every move at least three times and voting on the answer, which took over 3 million LLM calls. The Hanoi transformer makes all 1,048,575 moves for 20 disks with one small block, without tools, votes or second attempts.

Extra loops do not change its answer, since running its block 4 or 8 times per move instead of 2 produces the same moves. It only moves the stack from the first peg to the third, and from any other starting position it does not finish. It needs 64-bit numbers, because with 32-bit numbers rounding errors could pile up over a million moves. Its context window, the number of tokens it can read, is sized so that 20 disks is the most it can handle.

Checker Jumping. This is the second puzzle in the Apple study. Red and blue checkers sit in a row with one gap and must swap sides. They move only forward, either sliding into the gap or jumping a single checker of the other color. In the paper's tests, Claude 3.7 Sonnet Thinking and DeepSeek-R1 failed from about 3 checkers per side, while o3-mini on its high setting held about 50% or better up to 8 per side (read from the paper's figures). In 2026 tests, GPT-5.2 at low effort fell below 20% from 9 per side and to about zero by 11 (Pushkin and Abbe, 2026, read from a plot).

The Checker Jumping transformer works like the Hanoi transformer. Its attention reads the board and every move so far, its block computes the next move, and it stops when no move is left. It has 11,062 weights and is built for boards of up to 40 checkers per side, well beyond the Apple paper's largest size of 15. Claude checked it only on boards of up to 3 per side, yet it solves every size from 4 to 40 per side in the fewest possible moves, 1,680 of them at 40 per side.

HWritten transformers as test cases for interpretability

Knowing what every number means also makes the written transformers useful to interpretability research. Tracr compiles programs into transformers as a laboratory for testing interpretability methods on models whose algorithm is known [16]. InterpBench later trained such models to score methods that search for circuits [17]. The transformers in this post add looped models that solve hard benchmarks, with a known meaning for every number at every loop. A method that claims to find the algorithm inside a looped model can be checked against them, since the right answer is already written down.

IRelated work

Writing weights. Weight-Space Programming named the idea and showed LLMs reading and editing a model's weights directly. AdderBoard showed coding agents hand-setting the weights of tiny transformers. At the same time, Singh had Claude set every weight of small transformers for ten algorithmic tasks, including parity. Chaubard compares weight-space programming with ordinary training on small algorithmic tasks. Earlier, LLMs wrote programs that a compiler turned into weights (Weng et al., TracrBench).

Hand-built and compiled transformers. Programs have long been compiled into transformer weights (Tracr, and ALTA, which also compiles looped programs for parity and addition). Looped transformers can simulate general programs (Giannou et al.). Closest to our tasks are hand-constructed looped transformers that run breadth-first search, depth-first search and Dijkstra's algorithm (Back de Luca and Fountoulakis), a hand-built transformer for parity (Chiang and Cholak), and programs in RASP, a programming language that maps onto transformers, for balanced brackets (Weiss et al.). Compiled and semi-synthetic transformers also serve as test beds for interpretability methods (Tracr, InterpBench).

Trained models that handle bigger inputs. With special training recipes, trained models do handle inputs longer than the ones they saw. Looped transformers handle longer parity inputs when the loop count grows with the input (Fan et al., over 40 bits) or when the loop also carries state from token to token (Zhang et al., 256 bits). Transformers track variable chains longer than those seen in training (Wu et al.). Models that reason in a hidden loop and are trained on every intermediate step do this too (Altabaa et al.), as do graph neural models trained on algorithms' step-by-step runs (Ibarz et al.).

Looped models. Trained recursive reasoners such as HRM, TRM, LDT, EBR, FPRM and Looped Flows set the Maze-Hard results we compare against. Overthinking was named for recurrent models by Bansal et al. Overthinking in looped language models is studied by Blayney et al. and addressed with training by STARS. Methods that need no training, which change how a looped language model writes its answer or how many loops it runs, have also been tried (Liu et al., Wang et al.). LT2 saw attention pile up on the first token, loop after loop, in a looped transformer.
